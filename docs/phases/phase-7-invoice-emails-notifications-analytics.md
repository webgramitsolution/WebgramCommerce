# Phase 7: Invoice, emails, notifications, analytics (0.8.0)

### A. Implemented

Webgram Core
- Analytics (`Analytics` module): `wg_events` table (event, object type and id, user id, hashed session, meta without personal keys, created at; no IP addresses), `POST webgram/v1/events` batched collector (REST nonce, per IP rate limit, batch of 20, pure validation against an allow list extendable through `webgram_core/analytics/allowed_events`, personal keys such as email and phone stripped from meta), client helper `WebgramCore.track()` with queueing, sampling and `sendBeacon` on page hide (the reels, assistant, wishlist and compare events from earlier phases now land in the table), server side events through `webgram_core/analytics/event` (and the alias `webgram_core/event`), server side product views on product pages (works without JavaScript, sampled), `webgram_core/trending/views` provider for the daily trending score, retention on the daily maintenance cron, WordPress privacy exporter and eraser, settings (collect, sampling percent, track staff, retention days) and the Webgram > Analytics page: cards for assistant conversations, reel plays, wishlist adds, product views and the WhatsApp delivery rate, inline SVG bar sparklines (no chart library), top reels and products, and all event counts for 7 or 30 days.
- Invoice (`Invoice` module): `wg_invoice_sequence` table where the AUTO_INCREMENT id is the gap free sequence and UNIQUE(order_id) makes assignment idempotent; assignment in a transaction with a pending placeholder, three attempts on a UNIQUE(invoice_no) collision; pure numbering (`{prefix}{number}{suffix}`, `{yyyy}`, `{yy}`, `{mm}`, `{fy}` Indian financial year, padding, starting number, yearly restart by calendar or financial year); numbers stored on the order (`_wg_invoice_number`, `_wg_invoice_date`) and never regenerated. `InvoiceData::from_order()` normalizes store, customer, order (payment line with transaction id, shipping method, status), items (image, variation attributes, SKU, HSN from `_wg_hsn`, quantity, unit price, discount, per item taxes classified as CGST, SGST, IGST, UTGST, VAT or other), totals (subtotal, discount with coupon codes, shipping, fees, classified taxes with rates, refunds, grand total), notes, disclaimer and colors, with the `webgram_core/invoice/data` filter. A4 template per spec 4.11 (logo and tagline left, contact block with icons, navy INVOICE box with number, order date, payment date and status, thin rule, three columns Billing, Shipping and Order Information with dividers, dark header items table with thumbnails, bold names and grey variation lines, optional SKU and HSN columns, zebra option, grey Payment Information and Notes boxes, totals with green negative discount and highlighted Grand Total, footer with company and GSTIN, Need Help block, social and website, bottom strip with the disclaimer and generation time; table based, restricted CSS, DejaVu Sans). `PdfGeneratorInterface` with `DompdfGenerator` (dompdf 3.1 vendored through Composer with `composer.json` and lock committed and `vendor/` ignored, A4 portrait, remote images limited to the site's own host, fonts cached under uploads) and `HtmlGenerator` fallback (printable HTML when dompdf is missing). Storage under `uploads/webgram-invoices/{yyyy}/{mm}/` with `index.html` and `.htaccess` deny. REST `GET webgram/v1/invoice/{order_id}` served only to shop managers, the logged in owner, a valid order key (thank you page) or a signed temporary token (WhatsApp document links, 7 days); `regenerate=1` for managers. Admin: order row action, order metabox (number, date, download, generate or regenerate with notices), bulk action "Download invoices (zip)" on both the legacy and HPOS order screens with a one time token download, dompdf hint when missing. Customer: My Account orders action through `woocommerce_my_account_my_orders_actions` (rendered by the theme's order actions and by any other theme), thank you button through `webgram/thankyou/after_details` with a `woocommerce_thankyou` fallback for other themes. HSN field in the Webgram product panel when the HSN column is on. Settings: store fields (logo, legal name, tagline, address, phone, email, website, GSTIN, PAN, CIN, support line, footer note, social), numbering, trigger (payment complete, processing or completed, manual), layout toggles, colors, disclaimer. `attachment_for()` for the Emails module.
- Emails (`Emails` module): branding settings (logo and width, header, page, content, text, link, button colors, button radius, width, email safe font family, footer text with placeholders, social links, invoice attachment email ids), pure token validation and CSS builder, `woocommerce_locate_template` swap of only `email-header.php`, `email-footer.php` and `email-styles.php` when "Use Webgram email templates" is on (a theme override still wins), templates keeping every WooCommerce id and the `woocommerce_email_footer_text` filter, extra rules through `woocommerce_email_styles`, footer text placeholders, Webgram > Email preview page (any WooCommerce email rendered with the latest order in an iframe, open in a new tab, test send to the admin through `wp_mail`), invoice attachment through `woocommerce_email_attachments` delegating to the Invoice module (no PDF code here). Delivery stays with `wp_mail()`.
- Notifications (`Notifications` module, files exactly as specified): `Channels/ChannelInterface`, `EmailChannel` (the event matrix enables or disables WooCommerce's own emails through `woocommerce_email_enabled_{id}`; Shipped and Out for delivery emails are sent through the WooCommerce mailer wrapper so the Emails branding applies; no SMTP), `WhatsAppCloudChannel` (owner's Phone Number ID, WABA ID, encrypted access token, editable Graph API version; ### E. Errors found and fixed

- `Helpers::calling_code()` returned nothing outside WooCommerce, which broke phone normalization in the harness and in any early hook before WooCommerce loads; added a fallback table of common calling codes.
- Harness expectation for the analytics batch cap was written against the input cap; corrected.
- The WhatsApp template documentation was first written to a folder that did not exist; created `webgram-core/docs/`.

### F. Compatibility concerns

- Yearly reset numbering counts earlier rows in the same period inside the transaction; two orders paid in the same instant can collide once and are retried with the next number, so numbers stay unique but may not be strictly ordered by payment time under heavy concurrency.
- The invoice PDF needs the Composer vendor folder; the release zip built in Phase 8 must include it. Until then the HTML fallback serves a printable page and email attachments are skipped (never an HTML attachment).
- The email template swap respects theme overrides in `{theme}/woocommerce/emails/`; plugins that also filter `woocommerce_locate_template` at priority 20 or later win over Core.
- The WooCommerce checkout block does not render classic checkout fields, so the WhatsApp consent checkbox appears only on the classic checkout and in My Account; block checkout consent needs the WooCommerce Blocks checkout fields API (planned for a later release).
- Meta requires approved Utility templates; the module maps only synced templates and skips sends without a mapping (`skipped_no_template`).
- Action Scheduler ships with WooCommerce; without it the queue falls back to single WP cron events.

### H. Known limitations

- Invoice numbers are assigned per store, not per currency or per tax registration; multi GSTIN stores need separate sequences (extendable through the numbering filters later).
- The invoice template ships one layout (colors, logo and column toggles configurable); alternative layouts can be added as theme overrides at `{theme}/webgram-core/invoice/invoice.php`.
- Email preview uses the latest real order; stores without orders see a notice instead of a mock order.
- The notification log stores masked recipients and hashes only, so searching by phone number is not possible by design.
- BSP and SMS channels are interfaces without providers in v1.
